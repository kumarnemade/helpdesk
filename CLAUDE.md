## Structure

Bun workspaces monorepo:

- `core/` — shared code imported by both `client` and `server` as package `core` (`"core": "workspace:*"`). Plain TypeScript with no build step: `package.json` `exports` points at `src/index.ts`, which Bun and Vite consume directly. Holds Zod schemas and the constants they use, one module per domain (e.g. `core/src/users.ts`: `createUserSchema`, `MIN_PASSWORD_LENGTH`), re-exported from `core/src/index.ts`. Must stay runtime-agnostic: depend only on `zod`, never on Express, Prisma, React or browser/Node APIs.
- `server/` — Express 5 + TypeScript, run directly by Bun (no compile step). Entry `src/index.ts`, app setup in `src/app.ts`, routers in `src/routes/`. All API routes live under `/api`.
- `server/prisma/` — Prisma 7 schema and migrations; config in `server/prisma.config.ts`. The client is generated into `server/src/generated/prisma` (git-ignored) and connects through the `@prisma/adapter-pg` driver adapter. Import the shared instance from `server/src/db.ts`; never create another `PrismaClient`.
- Auth — Better Auth (email/password, database sessions) configured in `server/src/auth.ts`; its handler is mounted at `/api/auth/*splat` **before** `express.json()`. `trustedOrigins` comes from the required `CLIENT_ORIGIN` env var (the server throws at startup if it's missing). Protect routes with `requireAuth` (`server/src/middleware/requireAuth.ts`), which puts `user`/`session` on `res.locals`; mount `requireRole('admin')` (`server/src/middleware/requireRole.ts`) after it on admin routes (e.g. `app.use("/api/users", requireAuth, requireRole("admin"), usersRouter)`). Route handlers return users through an explicit `select`/field list so new columns aren't exposed by default. Startup also requires `BETTER_AUTH_SECRET` (32+ chars). Passwords must be 12–128 characters (`MIN_PASSWORD_LENGTH` / `MAX_PASSWORD_LENGTH` from `core`, used by Better Auth, `db:seed` and `createUserSchema`). Rate limiting is on only when `NODE_ENV=production` and is stored in the `rateLimit` table (sign-in: 5/min per IP). The client IP comes from Express's `req.ip`, so set `TRUST_PROXY` when the API runs behind a prox y. Responses go through `helmet`; errors that reach the error handler return only the standard status text (deliberate 4xx responses from routes may carry a user-facing message). Auth tables (`user`, `session`, `account`, `verification`) are in `schema.prisma`; Better Auth checks them against the generated client at startup. Public sign-up is disabled (`disableSignUp`) — users are created by an admin via `POST /api/users` (the "Create user" dialog on `/users`; always role `agent`), and the first admin via `db:seed`. Both use Better Auth's internal adapter (`createUser` + `linkAccount` with `ctx.password.hash`), which skips Better Auth's own password checks, so validate length yourself. Users have a server-owned `role` field (`admin` | `agent`, default `agent`, `input: false` so clients can't set it). Users are soft-deleted: `DELETE /api/users/:id` sets `User.deletedAt`, deletes their sessions and unassigns their tickets (`assignedToId` → null) in one transaction (admins can't be deleted → 403); the delete dialog says so and refreshes the users, tickets and assignee queries. A `databaseHooks.session.create.before` hook in `auth.ts` blocks sign-in for deleted users with the same 401 `INVALID_EMAIL_OR_PASSWORD` response as a wrong password. Any query for active users must filter `deletedAt: null`; a deleted user's email stays reserved (409 "This email belongs to a deleted user").
- Dashboard — `/` is `DashboardPage` (heading "Dashboard"; reached through the "Helpdesk" brand link and "Dashboard" in `NavBar`): one stats panel of five cells (the two AI stats in the `ai` colour) and, below it, `TicketsPerDayChart` (shadcn `chart` + Recharts bar chart of tickets received per day, with a visually hidden table of the same numbers for screen readers) from `GET /api/dashboard` (`server/src/routes/dashboard.ts`, `requireAuth`; query key `dashboardQueryKey`, helpers and `formatDuration` in `client/src/lib/dashboard.ts`), which takes `dashboardQuerySchema` (`core/src/dashboard.ts`: optional IANA `timeZone`, default UTC, invalid → 400; the client sends the browser's) and returns `{ totalTickets, openTickets, aiResolvedTickets, aiResolvedPercent, averageResolutionSeconds, ticketsPerDay }` computed in one `$transaction`: all tickets (including `processing`), status `open` only, tickets with an `ai` reply, their share of all tickets (one decimal), and the mean `resolvedAt - createdAt` over tickets with a `resolvedAt` (a `$queryRaw` `AVG(...)::float8`; `null` → "—"), and `ticketsPerDay` — `[{ date: "YYYY-MM-DD", count }]` for the last `DASHBOARD_CHART_DAYS` (30) days ending today in `timeZone`, oldest first, empty days as 0 (a `$queryRaw` over `generate_series`; `createdAt` is stored as zone-less UTC, hence `AT TIME ZONE 'UTC' AT TIME ZONE tz`). It refetches whenever the page is opened (default `staleTime`), so ticket mutations don't invalidate it.
- Client auth — `authClient` (Better Auth React client) in `client/src/lib/auth-client.ts`, no `baseURL` so it calls `/api/auth` on the same origin; `inferAdditionalFields` exposes `role` on the session user. `/login` is `LoginPage`; all other routes are wrapped in `ProtectedLayout`, which redirects to `/login` when there's no session. Admin-only pages (e.g. `/users`) are nested inside `AdminRoute` (`client/src/components/AdminRoute.tsx`) within `ProtectedLayout`, which redirects non-admins to `/`; `NavBar` shows admin links only when `user.role === 'admin'`. This is UI gating only — admin API routes must also check the role server-side.
- Tickets & inbound email — `Ticket` (`Int` autoincrement id, `subject`, the opening email's `body`/`bodyHtml`, `status` new/processing/open/resolved/closed default `new`, optional `category` with no default, required `senderName`/`senderEmail`, optional `assignedTo` user, unique `emailMessageId`, optional `resolvedAt` — set when the ticket becomes resolved or closed (by AI or `PATCH`), kept on resolved → closed, cleared when it goes back to new/open, including a customer reply reopening it) and `Reply` (`senderType` customer/agent/ai, `body`/`bodyHtml`, `senderName`/`senderEmail`, optional `author` user for agent replies (null for customer and AI replies), unique `emailMessageId`) in `schema.prisma`; status/category values are mirrored as `TICKET_STATUSES`/`TICKET_CATEGORIES` in `core/src/tickets.ts`; `AGENT_TICKET_STATUSES` (all but `processing`) are the statuses agents can filter by and set (`processing` is added at the end of the Postgres enum). `bodyHtml` is untrusted sender HTML — sanitise it before rendering. Email reaches the app two ways, both through `ingestEmail` (`server/src/ingestEmail.ts`, which holds the duplicate/threading/new-ticket logic below): the helpdesk's Gmail inbox, and a webhook. Gmail (optional; `GMAIL_USER` + `GMAIL_APP_PASSWORD`, an App Password; config, `emailConfigured` and the sender in `server/src/mailer.ts`): `pollGmailInboxJob` (`server/src/gmailInbox.ts`, `imapflow` + `mailparser`) runs every minute from a pg-boss schedule on the `poll-gmail-inbox` queue (`exclusive` policy, no retries; unscheduled at startup when Gmail isn't configured), reads unread INBOX email oldest first, maps it onto `receiveEmailSchema` (over-long text cut to the limit), skips the account's own address, `no-reply`/`mailer-daemon`/`postmaster` senders and auto-replies/lists (`Auto-Submitted`, `Precedence`, `List-*`, `X-Autoreply`) so AI replies can't loop with auto-responders, and marks each email read after storing or skipping it (a failure stops the poll and leaves the rest unread; email opened in Gmail before a poll is missed). Agent replies (`POST /api/tickets/:id/replies`) and AI auto-resolve replies are emailed to the customer when Gmail is configured: the reply gets a generated `emailMessageId` and a `send-reply-email` job (`{ replyId }`, same retries as classification) in the same transaction; `sendReplyEmailJob` sends it over Gmail SMTP (`nodemailer`, `service: "gmail"`) from the Gmail address with the reply's sender name, subject `Re: <subject>`, `In-Reply-To`/`References` from the ticket's earlier Message-IDs so it threads in the customer's mailbox (and their answer threads back onto the ticket), and sets `Reply.emailSentAt`, which a retry checks so it isn't sent twice. Gmail sends about 500 emails a day. The webhook: `POST /api/inbound-email` (`server/src/routes/inboundEmail.ts`) takes provider-agnostic JSON validated by `receiveEmailSchema` (`from`, `fromName`, `subject`, `text`, optional `html`/`messageId`/`inReplyTo`/`references`; Message-IDs stored without `<>`). It's mounted in `app.ts` **before** the global `express.json()` with its own 1mb parser and `requireWebhookSecret` (`Authorization: Bearer <INBOUND_EMAIL_SECRET>`, 32+ chars, required at startup) instead of a session. A `messageId` already stored on a ticket or reply returns 200 with that ticket (idempotent retries); an email whose `inReplyTo`/`references` match a non-closed ticket's own `emailMessageId` or one of its replies', from the ticket's `senderEmail`, is added as a customer `Reply` (reopening a resolved ticket), otherwise a new ticket is created (201). Responses are `{ ticketId, created }`. New tickets are classified and auto-resolved by background jobs: the ticket, a `classify-ticket` job and an `auto-resolve-ticket` job (both `{ ticketId }`) are created in one `prisma.$transaction` (`boss.send(..., { db: fromPrisma(tx) })`, only when `GOOGLE_GENERATIVE_AI_API_KEY` is set; threaded replies and duplicates queue nothing), so the jobs exist exactly when the ticket does and the webhook still answers immediately. Jobs run on pg-boss (`server/src/queue.ts`: the shared `boss` instance, queue names and options, `startQueue()`), stored in Postgres in its own `pgboss` schema, which pg-boss creates and migrates on start (Prisma only manages `public`). `server/src/index.ts` awaits `startQueue()` before `app.listen` (the webhook needs it), registers the workers only when the AI key is set (without it, startup moves any `processing` tickets to `open`), and calls `boss.stop()` (waits up to 30 s for running jobs) before disconnecting Prisma on shutdown. The worker `classifyTicketJob` (`server/src/classifyTicket.ts`) parses `job.data` with Zod, skips deleted or already-categorised tickets, picks one of `TICKET_CATEGORIES` with `classifyTicket` in `server/src/ai.ts` (`Output.choice`, same Gemini model, 30 s timeout plus the job's abort signal) from the subject and plain-text body, and saves it with `updateMany` where `category: null` so an agent's choice is never overwritten. It throws on failure so pg-boss retries (3 retries with backoff from 30 s; a job active over 60 s is retried); jobs survive server restarts. Auto-resolution (`autoResolveTicketJob` in `server/src/autoResolveTicket.ts`, same retries) moves a `new` ticket to `processing`, asks `autoResolveTicket` in `server/src/ai.ts` (`Output.object` → `{ action: resolve | escalate, reply }`, 30 s timeout) whether `server/knowledge-base.md` (read once at startup by `server/src/knowledgeBase.ts`; restart to pick up edits) fully answers the opening email with none of its escalation rules applying, then either saves an `ai` reply (written by the AI agent: sender "AI" / `ai@helpdesk.local`, `author` the AI agent user; emailed to the customer when Gmail is configured) and sets `resolved` in one transaction, keeping the ticket assigned to the AI agent, or sets `open` and unassigns it from the AI agent. The AI agent is a user named "AI" with role `agent` and email `AI_AGENT_EMAIL` (`ai@helpdesk.local`, `server/src/aiAgent.ts`: `findAiAgentId()`), created by `db:seed:ai-agent` without a credential account, so nobody can sign in as it; when AI is configured, the webhook creates new tickets assigned to it. Without the AI agent (not seeded, or deleted) auto-resolution still runs, just without assigning, and startup logs a warning. It appears on `/users` like any agent but not in the assignee list (only auto-resolution assigns it; `PATCH` to it → 400 "Tickets can't be assigned to the AI agent"; a ticket it holds shows "AI" as a disabled item in `AssigneeSelect`); `db:seed:tickets` doesn't assign demo tickets to it. Every step requires the expected status (`updateMany`), and unassigning only applies while the AI agent is still the assignee, so an agent's change in the meantime wins. A job that fails every retry is copied by pg-boss to the `auto-resolve-ticket-failed` dead-letter queue, whose worker moves the ticket `processing` → `open`, so no ticket stays hidden. `startQueue()` calls `createQueue` then `updateQueue` for each queue (dead-letter queue first), so changed queue options apply on the next start. `GET /api/tickets` (`server/src/routes/tickets.ts`, `requireAuth` only — admins and agents) returns `{ tickets, total }` — one page of tickets through an explicit `select` without bodies, plus the number of matching tickets (both in one `$transaction`) — never including `processing` tickets (AI is still working on them; they appear once resolved or opened) — filtered, sorted and paginated on the server by the `listTicketsQuerySchema` query (optional `search` — case-insensitive `contains` on subject, sender name or sender email, LIKE wildcards escaped, max `MAX_TICKET_SEARCH_LENGTH` — and `status`/`category` filters from `ticketFiltersSchema`; `category=none` matches uncategorised tickets; `sortBy` one of `TICKET_SORT_FIELDS` — `assignedTo` sorts by assignee name — and `sortOrder` asc/desc, default `createdAt desc`; `id` breaks ties; `page` (1-based, default 1) and `pageSize` (one of `TICKET_PAGE_SIZES` 10/25/50, default `DEFAULT_TICKET_PAGE_SIZE` 10); a page past the end is empty but keeps `total`; invalid values → 400). The client shows them on `/tickets` (`TicketsPage` → `TicketsTable` (columns Subject, From, Status, Category, Received — no assignee column; the server's `assignedTo` sort is unused by the UI), a TanStack Table v9 `useTable` with `manualSorting`, `manualFiltering` and `manualPagination` (`rowCount: total`, `TicketsPagination` below the table): clicking a header, changing a `TicketFilters` dropdown or typing in its search box (global filter, debounced 300 ms, URL updated with `replace`) refetches under `[...ticketsQueryKey, query]`; search, filters and pagination live in the URL (`/tickets?search=refund&status=open&page=2`; page 1 and the default page size are omitted, invalid values ignored; sort/filter/search changes reset to page 1 and a page past the end moves to the last page) so filtered views can be linked to, helpers and display labels in `client/src/lib/tickets.ts`), linked from `NavBar` for every user. Each subject links to `/tickets/:id` (`TicketDetailPage`, read-only), passing the list's query string as router state (`TicketLinkState`) so "Back to tickets" restores the view. It loads `GET /api/tickets/:id` (`requireAuth`; id validated by `ticketIdParamsSchema` → 400 "Invalid ticket id", 404 "Ticket not found"), which returns `{ ticket }`: the list fields plus the plain-text `body` and `updatedAt` — never `bodyHtml`, the Message-ID or replies; the page shows the opening email as plain text, with replies loaded separately (below). Status, Category and Assigned to on that page are dropdowns (`StatusSelect`, `CategorySelect` with an "Uncategorised" option, `AssigneeSelect` listing Unassigned + active users) that save immediately through the shared `useUpdateTicket` hook (`client/src/hooks/useUpdateTicket.ts`: `useMutation` that sets the detail query data and invalidates `["tickets"]`; each shows the choice while saving and falls back to the saved value with a `role="alert"` on failure). Assignees come from `GET /api/tickets/assignees` (`requireAuth`; every user with `deletedAt: null`, agents and admins, except the AI agent, as `{ users: [{ id, name }] }`, registered before `/:id`). Saving is `PATCH /api/tickets/:id` (`requireAuth`, so admins and agents can both edit), a partial update validated by `updateTicketSchema` — any of `assignedToId` (user id, or null to unassign), `status` (any of `AGENT_TICKET_STATUSES`, no workflow rules; `StatusSelect` shows a disabled "Processing" item while a ticket is in it) and `category` (or null for uncategorised), at least one required (`{}` → 400 "Nothing to update"); fields not sent are unchanged; an unknown or deleted assignee → 400 "Assignee not found", missing ticket → 404; returns `{ ticket }` like the GET. Below the opening email the page shows a "Replies" section: `ReplyThread` (`GET /api/tickets/:id/replies`, `requireAuth`; 400/404 like the GET; `{ replies }` oldest first (customer, agent and AI replies, each with a badge) through an explicit `select` — `id`, plain-text `body`, `senderType`, `senderName`/`senderEmail`, `createdAt`, `author { id, name }`, never `bodyHtml` or the Message-ID; query key `ticketRepliesQueryKey(id)`, under the detail key) and `ReplyForm` (React Hook Form with `createReplySchema` from `core`: trimmed `body`, 1–`MAX_EMAIL_BODY_LENGTH` chars; "Send reply" and "Polish" are disabled while the draft is empty or whitespace, so no empty-reply error is shown). Submitting calls `POST /api/tickets/:id/replies` (`requireAuth`, admins and agents), which creates an `agent` reply whose author, sender name and email come from the signed-in user (never the request body), leaves the ticket status unchanged, emails it to the customer when Gmail is configured (above), and returns 201 `{ reply }`. On success the thread is refetched and the form cleared. Next to "Send reply", a "Polish" button (disabled while the draft is empty) validates the draft with the same rules and calls `POST /api/tickets/:id/replies/polish` (`requireAuth`; `polishReplySchema`; 400/404 like the reply POST), which rewrites it with Google `gemini-3.5-flash-lite` through the Vercel AI SDK (`ai` + `@ai-sdk/google`, `generateText` in `server/src/ai.ts`, ticket subject and customer name as context; it ends with a sign-off signed with the signed-in agent's name from the session, replacing any existing one) and returns `{ body }` without saving anything; the form replaces the draft for the agent to review before sending. In the side panel below Status, Category and Assigned to, `TicketSummary` shows a "Summarize" button with a sparkles icon that calls `POST /api/tickets/:id/summary` (`requireAuth`; no body; 400/404 like the GET) — `summarizeTicket` in `server/src/ai.ts` summarises the subject, status, plain-text opening email and replies oldest first (never `bodyHtml`) and returns `{ summary }`; the summary shows in a bordered `Card` (sparkles + "Summary" heading; "- " lines rendered as a bulleted list, other lines as paragraphs, plain text only); it's a `useMutation`, so every click ("Regenerate summary" after the first) generates a fresh summary and nothing is cached or saved. `GOOGLE_GENERATIVE_AI_API_KEY` is optional — without it the server still starts, new tickets aren't auto-classified, and the polish and summary endpoints return 503 ("Reply polishing isn't configured" / "Ticket summaries aren't configured").
- Error reporting — Sentry, optional (nothing is sent without a DSN), errors only (no tracing/replay). ## Commands

Run from the repo root:

- `bun install` — install all workspace deps (Bun uses isolated installs; each workspace has its own `node_modules`)
- `bun run dev` — start API (http://localhost:3000) and client (http://localhost:5173) in watch mode
- `bun run typecheck` — type-check every workspace (core, client, server, e2e)
- `bun run test` — run client component tests (Vitest)
- `bun run build` — build both packages

Database (PostgreSQL `helpdesk` on localhost:5432; `DATABASE_URL` in `server/.env`, template in `server/.env.example`), run from `server/`:

- `bun run db:migrate` — create and apply a migration after editing `schema.prisma` (Prisma 7 does **not** regenerate the client; run `db:generate` afterwards)
- `bun run db:generate` — regenerate the Prisma client (also runs on `bun install`)
- `bun run db:studio` — open Prisma Studio
- `bun run db:seed` — create the admin user from `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` (`prisma/seed.ts`; safe to re-run)
- `bun run db:seed:ai-agent` — create the "AI" agent user (`ai@helpdesk.local`, no password) that new tickets are assigned to during AI auto-resolution (`prisma/seed-ai-agent.ts`; safe to re-run)
- `bun run db:seed:tickets` — insert 100 varied demo tickets (statuses, categories, assignees from active users, senders, dates over the last 90 days) for trying out sorting/filtering (`prisma/seed-tickets.ts`; deterministic and safe to re-run — existing seed tickets are skipped)

Always run Prisma through these scripts (`bun --bun prisma ...`) so Bun loads `.env`. Keep `prisma`, `@prisma/client` and `@prisma/adapter-pg` on the same exact version.

Add a dependency to one workspace: `bun add <pkg> --cwd server` (or `--cwd client` / `--cwd core`). To use `core` from another workspace: `bun add core@workspace:* --cwd <workspace>`.

## Conventions

- Use Bun, not npm/yarn/pnpm or node.
- Always use `axios` with TanStack Query for client API calls — never raw `fetch` or `useEffect` + `useState` data loading (see `client/src/components/UsersTable.tsx`). Reads use `useQuery` with a descriptive `queryKey` (e.g. `['users']`) and pass the query function's `signal` to axios so stale requests are cancelled; writes use `useMutation` and invalidate the affected query keys on success. Call relative `/api/...` paths; Vite proxies `/api` to `localhost:3000` in dev. Use the shared `queryClient` (`client/src/lib/query-client.ts`, provided in `main.tsx`) — don't create another; it doesn't retry 4xx responses, retries others once, and is cleared on sign-out. (Better Auth calls still go through `authClient`.)
- Destructive actions (delete, etc.) confirm in a shadcn `AlertDialog` (see `client/src/components/DeleteUserDialog.tsx`): run the `useMutation` from the action button with `event.preventDefault()` so the dialog stays open until the request succeeds, show failures in a `role="alert"` inside the dialog, and reset the mutation when it closes.
- All forms use React Hook Form with a Zod schema via `zodResolver` (see `client/src/pages/LoginPage.tsx`, and `client/src/components/CreateUserDialog.tsx` for a form in a dialog that submits with `useMutation`, maps a 409 onto a field and resets on close): infer the values type with `z.infer`, set `noValidate` on the `<form>` so Zod owns validation, show field errors under each input with `aria-invalid`, and report server errors with `setError('root', …)`. Zod is v4 — use top-level formats like `z.email()`.
- Express 5 forwards rejected promises from async handlers to the error handler — no try/catch wrappers needed. Errors return JSON `{ error }`; 5xx responses hide internal details.
- Use Zod (v4) for all data validation — never hand-written `if` checks or another validation library. This covers request bodies, query strings and route params on the server, and form inputs on the client. Derive TypeScript types from schemas with `z.infer` instead of declaring them separately.
- Define every schema that describes API input (request bodies, query strings, params) in the `core` package, never inline in a route or component:
  1. Add it to the domain module in `core/src/` (create one, e.g. `core/src/tickets.ts`, and re-export it from `core/src/index.ts`). Name it `<action><Entity>Schema` (e.g. `createUserSchema`) and export its type next to it: `export type CreateUserInput = z.infer<typeof createUserSchema>`. Put shared limits in exported constants (e.g. `MIN_PASSWORD_LENGTH`) instead of repeating numbers.
  2. Include normalisation (`.trim()`, `.toLowerCase()`) and user-facing error messages in the schema, so client and server behave and read the same.
  3. Server: `import { createUserSchema } from "core"` and `safeParse` it in the route (see below).
  4. Client: pass the same schema to `zodResolver`. Type the form with `useForm<z.input<typeof schema>, unknown, z.output<typeof schema>>` so fields hold raw input and the submit handler gets the parsed values, and send those parsed values to the API (see `client/src/components/CreateUserDialog.tsx`). Type API helpers with the exported input type (`client/src/lib/users.ts`).
  5. Only form-only fields that never reach the API (e.g. a "confirm password" field) belong in a client-side schema, built by extending the core one (`createUserSchema.extend({...}).refine(...)`).
- On the server, parse with `schema.safeParse(req.body)` (or `req.query`/`req.params`) at the top of the handler and use only `parsed.data` afterwards; on failure return 400 `{ error }` with the first issue message (see `server/src/routes/users.ts`). Return 409 for conflicts such as a duplicate email. On the client, map 409 to the relevant field and other errors to `setError('root', …)`.
- Server TypeScript is strict with `noUncheckedIndexedAccess`; keep `bun run typecheck` passing.

## Testing

Rely mostly on component tests. Cover UI behaviour (rendering, states, forms, sorting/filter wiring, role-dependent UI) with Vitest component tests. Write an E2E test only when the behaviour can't be checked with the API mocked:

- the server's real response (auth/401/403, Zod 400s, query results such as sort order, fields hidden by `select`)
- a real session or redirect (sign-in, sign-out, protected and admin-only routes)
- a critical flow across several pages that must work end to end

E2E is only for those three cases. Never write an E2E test for anything a component test covers or could cover with the API mocked — static text, headers, role-dependent links, loading/error/empty states, form validation, dialogs, how the UI shows a server error — and never mock the API with `page.route()` in E2E (a test that needs a mocked API is a component test). Before adding an E2E test, check the component tests for the same page; if a UI behaviour isn't covered yet, add the component test instead. Don't check the same thing twice in E2E (e.g. an API test plus a UI test of the same server result).

### Component tests (client)

Stack: Vitest + jsdom + React Testing Library, configured in the `test` block of `client/vite.config.ts`. `client/src/test/setup.ts` loads the jest-dom matchers (`toBeInTheDocument`, `toHaveTextContent`, …) and runs `cleanup` after each test. Reference example: `client/src/components/UsersTable.test.tsx`.

When to write them: add or update component tests in the main session whenever you create or change a page or component with its own logic (data loading, conditional rendering, form validation, role-dependent UI). Component tests cover a single component's states with the API mocked and are the default for any UI change; full flows across the real server go in E2E only when the criteria above apply.

Writing them:

- File next to the component as `<Component>.test.tsx` (only `src/**/*.test.{ts,tsx}` is picked up).
- Vitest globals are off — import `describe`, `it`, `expect`, `vi`, `afterEach` from `vitest`.
- Render anything that uses TanStack Query with `renderWithQueryClient` from `@/test/render` (fresh `QueryClient` per test, retries off so error states appear immediately). Wrap in a `MemoryRouter` if the component uses React Router.
- Mock the API at the axios boundary: `vi.spyOn(axios, 'get').mockResolvedValue({ data: … })` (or `mockRejectedValue` for errors, `mockReturnValue(new Promise(() => {}))` to hold it pending), and call `vi.restoreAllMocks()` in `afterEach`. Assert the request too (URL, and `{ signal: expect.any(AbortSignal) }` for queries).
- Cover every state the component renders: loading (skeletons + the `sr-only` label), success with realistic data, empty, and error (`role="alert"`). For forms, cover validation errors and the server-error `root` message.
- Simulate interaction with `@testing-library/user-event` (`const user = userEvent.setup()`, then `await user.click(…)` / `await user.type(…)`); see `client/src/components/CreateUserDialog.test.tsx` for a form in a dialog, including mocking an `AxiosError` response. Radix dialogs render in a portal, so query them with `screen.findByRole('dialog', { name })` and scope with `within(dialog)`.
- Query like a user: `getByRole` (with `name`) first, then `getByText`/`getByLabelText`; use `findBy…` to wait for async content and `queryBy…` with `.not.toBeInTheDocument()` for absence. Don't select by Tailwind classes; a `data-slot`/`data-variant` attribute is fine when it's the only visible distinction (e.g. badge variants).
- Keep tests deterministic: build expected dates with the same `toLocaleDateString()` call the component uses instead of hard-coding a locale format.

Running them (from the repo root unless noted):

- `bun run test` — run the whole suite once (do this before committing; it should pass alongside `bun run typecheck`).
- From `client/`: `bun run test:watch` re-runs on save while writing tests; `bun run test:ui` opens the Vitest UI in the browser (open the `?token=` URL it prints); `bunx vitest run src/components/UsersTable.test.tsx` runs one file; add `-t "empty state"` to run tests whose name matches.
- Don't use `bun --bun vitest` — jsdom fails under Bun's runtime, so Vitest runs on Node.

### End-to-end tests

- Use the `e2e-test-writer` subagent (`.claude/agents/e2e-test-writer.md`) to write or update Playwright E2E tests rather than writing them in the main session; it holds the test setup and conventions. Launch it only when the user asks for E2E tests, or when a change meets the criteria at the top of this section — in that case tell the user why E2E is needed and ask first.
- In the prompt, name the feature or flow to cover and the files involved (pages, routes, endpoints) so it doesn't have to rediscover them.
- Running the tests resets `helpdesk_test`, which Prisma blocks for AI agents, and the subagent can't ask the user. Before launching it, ask the user whether it may run the tests. If they agree, include their exact reply in the prompt as consent for `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION`. Otherwise tell it not to run them; it will only type-check and list the tests, and the user runs `bun run test:e2e`.
- When it finishes, report whether the tests were actually run and passed, and pass on any `data-testid` or source changes it suggests.
